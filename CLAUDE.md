## Architecture

```
Next.js Public Websites (active)     Flutter Web Admin Portal
              ↓                                ↓
         Azure Function .NET Shim (stable, rarely changes)
                            ↓
         SQL Server Stored Procedures (domain logic lives here)
                            ↓
                    SQL Server Tables
```

**Key rules:**
- All frontends call stored procedures only via the API shim
- No direct DB access from any frontend. Ever.
- No dynamic SQL. Ever.
- The API is a transport layer only — logic lives in the database

**Auth (Flutter portal):** Device-bound shared secret → short-lived (30s) cryptographic token

**Auth (Next.js public web — admin):** One-time token generated by the Flutter portal
(via `hcportal_generateWebAdminToken`) → passed as `?token=` in the URL →
`/api/admin/auth` redeems it against `HC.PublicWebAdminToken` → sets an HMAC-signed
httpOnly session cookie (`hc_admin_session`, 24h). Requires `HC_ADMIN_SESSION_SECRET`
env var set in Azure App Service. Flutter user must have `AppAccessFlags & 0x00000001`
for the kennel.

**Auth (Next.js public web — member):** the browser registers as a device
(E9.F7) and mints the same tokens the phone does. See `public-web/CLAUDE.md`.

## Non-Negotiable Design Decisions

These are firm decisions that must not be revisited or worked around:

- **Never create a new database table without asking James first.** James does
  not want tables to proliferate: the default answer is a column on an existing
  table, and a new table is the exception he chooses, never the convenience the
  code reaches for. A table is schema, and schema is a product decision: it changes what the database
  *is*, it outlives the feature that wanted it, and every later SP, sync
  domain, retention job and backup has to know about it. When a feature
  seems to need a new table, stop and put the choice to James — what the
  table would hold, why an existing table (or a column on one) will not do,
  and what it costs to keep — and build only after he has chosen. This
  applies to run-once create scripts as much as to `db/schema/tables/`.
  Added 2026-09-10 after `HC.EventTrackRunner` was created unasked.

- **Run-card data is synced, never fetched while scrolling.** Anything the
  main run screen's cards show — the track icon and runner count, photo, chat
  and down-down counts, the hasher's own trail — lives on a synced row
  (`HC.Event` activity counts kept by triggers through
  `HC6.nonApi_refreshEventActivity`; the hasher's own `TrackGzip` on their
  `HasherEventMap` row in the user sync) and is read from the phone's
  database. A card must not call the server for what it displays: the list
  has to look the same offline as online, and a screenful of cards must not
  become a screenful of requests. New card content follows the same path —
  a column on the synced row, maintained server-side where it changes, never
  an on-demand SP per card or per screen. (James, 2026-09-12; E5.F7.S1.)

- **Public web auth must NOT use username/password.** The public web admin
  (page builder, content management) authenticates via a one-time token
  generated by the Flutter portal and passed in the URL — the same trust
  model the portal already uses. No email/password login, no NextAuth
  credentials provider, no separate user account system for admins.

- **Run editing in the portal and in the app are ONE feature, kept in sync
  (James, 2026-10-09).** Whatever a run admin can do to a run in the app —
  edit it, send it, email it, preview the email, see who gets it — they can
  do in the portal, and the other way round, with the same rules, the same
  stored procedures where the client allows it, and the same outcome. A
  capability added to one side is not finished until it is on the other
  (Save and send shipped in the app on 1451; the portal got Email members
  the same day, then Preview and Who gets it had to be added to both). When
  only one side can have something for a technical reason, the gap goes in
  the backlog as a Known gap, never left silent.

- **The Facebook integration is defunct (James, 2026-10-10).** Facebook no
  longer allows the Graph API access it relied on, so importing runs from
  Facebook groups and pages is gone for good (`HC.Integration` 1 "Import from
  Facebook Groups", `Enabled = 0`; the last run it imported was 2026-06-20).
  Code that exists ONLY for that integration may be removed whenever it is
  touched: the `IntFacebook` path in `api/Endpoints/HcExternalDataIntegration.cs`,
  Facebook token handling and token-expired emails (`KennelFacebookToken*`,
  `IntegrationSendTokenExpiredEmails`), "Facebook" as an integration choice in
  the portal and app, and help text that promises a Facebook data exchange
  (the app FAQ). **What must stay:**
  - **The `Fb*` mirror columns, the `UseFb*` flags, `EventFacebookId` and
    `InboundIntegrationId` on `HC.Event`, and the logic that reads them.** They
    hold 5,092 historical Facebook runs, AND every live import writes through
    them under the Facebook name: San Diego (integration 3, 1,791 runs),
    Berlin (5, 364), the runs-page import (6, `EventFacebookId` =
    `runspage:<n>`). They are the generic import mirror, misnamed — never
    drop or repurpose them as "Facebook clean-up".
  - **Facebook as a link.** A kennel's Facebook page or group is a social link
    like Instagram (`E12.F4.S4`), not the integration.
  87 kennels still have `InboundIntegrationId = 1`; resetting them is a data
  change for James to approve, not part of a code clean-up.

- **Membership is `MembershipExpirationDate` in the future, nothing else
  (James, 2026-10-13).** Never store, sweep or read a derived "is member"
  flag. Bit 0x0001 of `HC.HasherKennelMap.KennelStanding` (the old automated
  MEMBER bit) is RETIRED: nothing read it, and keeping it in step cost a
  nightly re-sync of every lapsed row to every phone. Its values are frozen
  and meaningless; do not reuse the bit. The manual standing bits (ALUMNI
  0x0002, TRUSTED 0x0004, ADMIN 0x0100, notes suppressed 0x1000) stay.
  A computed column was considered and rejected: the field mixes manual
  bits, and a time-dependent value never bumps `updatedAt`, so synced
  phones would never see it change.
  **`HC.HasherKennelMap.IsMember` is DEPRECATED** for the same reason: a
  stored copy of the date, set at join and never maintained. On 2026-10-13
  it disagreed with the date on 1,839 rows, and hasher search read it.
  Never read it; compute `MembershipExpirationDate > SYSDATETIMEOFFSET()`.
  The old writers (join, approve kennel request, merge) still set it and
  carry a DEPRECATED comment; dropping the column is James's call.

- **TSA Eats is defunct — exclude it from all work (James, 2026-10-13).**
  TSA Eats was a separate meal-ordering prototype that shares this repo and
  database but is not Harrier Central. Leave it out of everything: reviews,
  audits, contract sweeps, scans, backlog stories, refactors, deploys and
  release plans. Do not read, fix, test or document it unless James names it.
  It lives in `tsa-eats/`, `db/hc6/tsa/`, `db/schema/tables/TSA.*`, the
  `TSA` database schema and `api/Endpoints/TsaApi.cs`. `deploy_hc6.sh` never
  deploys it, and `tools/contract_check.py` does not scan it. Removing its
  code, endpoint or tables is a separate decision for James, not a clean-up
  to do in passing.
  **Ignore it everywhere it surfaces, without mentioning it (James,
  2026-10-14):** the `TsaApi` / `tsaapi` endpoint that every
  `func azure functionapp publish` lists (it is compiled into the API
  project — leave it, never filter, test or call it), the
  `harriercentraltsaeats` web app and any other TSA Azure resource, TSA rows
  in logs, `HC.ErrorLog`, sweeps and triage, and TSA objects in schema
  dumps or `sys.*` listings. Do not print, quote, count or report any of
  it; leave it out of command output you show James (filter it before
  printing, e.g. `grep -vi tsa`), and never include it in an inventory,
  a cost review or a "what is deployed" answer. TSA's own deploy
  (`reference_tsaeats_deploy`) is never run.

- **Never convert a `StatelessWidget` to `StatefulWidget` without consulting
  James first.** The preferred direction is the opposite — migrate
  `StatefulWidget` toward `StatelessWidget` + GetX controller wherever the
  state logic is non-trivial. If you find yourself reaching for `StatefulWidget`
  to get a lifecycle hook (e.g. `initState`, `didChangeDependencies`), stop and
  look for a GetX-native equivalent first: `GetxController.onInit()`,
  `onReady()`, `ever()`, `once()`, or `Get.context`. The only acceptable
  `StatefulWidget` cases are very simple, self-contained widgets with minimal
  local UI state (e.g. an animation or a focus node) that have no business
  logic and no reason to involve a controller.

## Guiding Principles

1. **Agents propose. James decides.** Never treat AI output as ready to
   commit without review.
2. **One SP at a time.** Each SP is its own commit. No batch refactors.
3. **Contracts before code.** Extract the HC5 contract before writing HC6.
4. **Break nothing silently.** Every breaking change must be deliberate
   and documented in the contract.
5. **Defer complexity.** Don't build tooling until the pain is real.
6. **Tired-James needs guardrails.** When in doubt, flag it — don't fix it.

## Production Deployment Rule

**Never trigger a production deployment autonomously.** All deployments to
production — whether the Next.js public web, the Azure Functions API shim, or
the SQL Server stored procedures — must be explicitly requested by James in the
conversation. Do not deploy as a side effect of making code changes, even if
asked to "make the change and push it."

The explicit request is either a specific deploy instruction ("deploy the API")
or one of the two release commands.

**"Dance baby!"** and **"I want a private dance"** are the release commands.
When James says either one, read `.claude/skills/dance-baby/SKILL.md` in full
and follow it. It is also available as `/dance-baby`. The skill never loads on
its own, so do not release from memory of an earlier session.

The deploy commands themselves are `ask` rules in `.claude/settings.json`:
`tools/deploy_hc6.sh`, `func azure functionapp publish`, `az webapp deploy`,
and any push to `master` (which deploys the portal through CI). Claude Code
stops for James's approval on each one, in every permission mode.

**Every public-web deploy gets its own version (James, 2026-10-15).** The web
has no build number, so each deploy bumps the last part of `"version"` in
`public-web/package.json` (and `package-lock.json`): 0.21.75 → 0.21.76, with
its own entry in `public-web/CHANGELOG.md` and `pubchanges.txt`. Never
redeploy under a version that is already live — 0.21.74 went out four times
on 2026-10-14, and the error triage (`fixed:web <version>`) could not tell
those builds apart. This is the one standing exception to "never bump a
version unasked"; the middle and first parts (0.**21**.x, **0**.21.x) still
change only when James asks.

**Significant AI work goes in the history too — unasked (James, 2026-10-15).**
`LOG.DeployLog` holds every deploy AND every significant piece of AI work, on
one timeline, never pruned, so either can be studied later ("what changed
just before this started?", "what did the June SP audit find, and did it
hold?"). Log it yourself when the work is committed, without being asked:

- **Counts:** audits, reviews and surveys of a whole area (SPs, a client's
  pages, permissions, costs, logs); error-log sweeps and triage; refactors and
  migrations that touch many files or SPs (a GetX migration, a contract sweep,
  a rule applied across the codebase); new rules, scans or tooling that change
  how work is done; data repairs and run-once scripts against production;
  schema changes; backlog-wide sweeps.
- **Does not count:** a single bug fix, one feature, one SP, a question
  answered. Deploys are logged by their own commands. When unsure, log it —
  a spare row costs nothing, a missing one is a gap in the record.

```bash
python3 tools/record_deploy.py ai-task "<title ≤ 40>" --detail "<what was examined or changed, ≤ 400>"
python3 tools/record_deploy.py --outcome <id> "<what it found, what was fixed, what went to James, ≤ 2000>"
```

Write the outcome as soon as it is known (often the same session), and come
back to it when something later changes the story (a fix shipped, a finding

## Cross-Cutting Conventions

**Delimited list parameters (SP and Dart):**

When passing a list of values as a delimited string parameter, always use `|` as
the delimiter — never comma. Commas appear in natural language and some data fields;
`|` is rarely used in real data and eliminates the risk of a value accidentally
splitting the list. Use `STRING_SPLIT(@param, '|')` on the SQL side and
`join('|')` / `split('|')` on the Dart side.

**Every user gesture is acknowledged at once (every client):**

Every gesture that starts work — a tap, click, double-tap, long-press, a
swipe-to-act, a drag that drops something, pull-to-refresh, toggle,
checkbox, slider, menu or picker choice, key press or form submit, in the
app, the portal or the public web — is answered **in the same frame**: a
spinner on the button, the control disabled or recoloured, a row spinner, a
progress bar, a "Sending…" toast, an optimistic change (James, 2026-10-14).
**Gestures whose own movement is the feedback need nothing more** —
scrolling, panning or zooming a map, swiping between tabs or pages, dragging
a thing that moves under the finger. The rule is about gestures that ask the
system to DO something: a write, a send, a fetch, a check, a navigation that
waits. Never a pause in which nothing
moves while a request, a check, a GPS fix, an upload or a dialog is
prepared. A gesture that shows nothing looks missed, and repeating it is how
one run was saved twice, then four times, and how a swipe paid twice.

- **Show it before the first `await`.** Set the busy state, then do the
  work; clear it in a `finally`. A save that first awaits a confirmation
  dialog or a pre-check is exactly where the gap hides (the portal's Save
  waited on the same-start check, E3.F1.S8, before showing "Saving...").
- **The busy state also refuses a second press** until the first returns.
  Portal: `HcButton(loading: …)` already spins and disables; the tabbed
  editors' Save goes through `TabUiController.saveFromButton()` and its
  `isSaving`. App and web: the same shape — a flag checked and set first.
- **Feedback is not idempotency.** A reply can still be lost and retried,
  so every write follows **Idempotent writes** below as well. Do both.

**Idempotent writes — every API call that writes (every client, every SP):**

Every call that writes to the database must be safe to arrive twice
(James, 2026-10-14). A write is repeated without anyone meaning it: a double
tap, a "try again" after a lost reply, and the app's own transport, which
retries a failed write up to six times (`ServiceCommon.sendHttpPost`,
`_maxRetryAttempts`) — after a timeout the server may already have committed.
The audit that found eight live cases (receipts, run emails, help pushes,
membership extensions, down-down charges …) is
`docs/idempotency-audit-2026-10-14.md`.

The pattern, by kind of write:

| The write… | Made idempotent by |
|---|---|
| **creates a row** (run, receipt, charge, message, photo, payment) | The client mints the GUID **once per user intent** — per editor, page or sheet, not per tap or per request — and sends it on every attempt until the server confirms. The SP checks for it `WITH (UPDLOCK, HOLDLOCK)`; found ⇒ return the existing result as success (or treat it as an edit). Never `NEWID()` for a row a client asked for. |
| **sets a state** (RSVP, attendance, a flag, a preference) | Already idempotent: write the state, never toggle or flip it. Send the target value, not "the opposite". |
| **adds or subtracts** (extend membership by N months, credit, a count) | Never a bare delta. Compare-and-set (send the value the client saw; apply only if it still holds, else return the current row as success), or send the absolute target. |
| **sends something** (email, push, a fan-out) | A client-minted send id, recorded BEFORE the send under the same lock; a repeat returns the recorded result and sends nothing. |
| **upserts by a natural key** | `MERGE … WITH (HOLDLOCK)` or a unique index on the key, so two concurrent firsts cannot both insert. |

Rules that go with it:
- A browser holds **public** ids only: the portal and the web mint the
  PUBLIC id for a new row and the SP resolves it at the door
  (`hcportal_addEditEvent @newPublicEventId`; `/hc-primary-keys`).
- A **failure that left the write unconfirmed keeps its id** for the retry; a
  success clears it. Minting a fresh id for "try again" defeats the point
  (the help-push case in the audit).
- A repeat answers **success with the original result**, never an error —
  the client must not show "already exists" for its own lost reply.
- A write that cannot be made idempotent opts out of the transport's
  automatic retries (`noRetries: true`) and says why in a comment.
- **A GET never acts.** A link in an email, a QR code or a share is fetched
  by mail security scanners (Safe Links, Mimecast), link previews and
  prefetchers before — or instead of — the person. A link may show a page;
  only a POST (a button on that page, RFC 8058 one-click) may write, send or
  consume a token. The run email's unsubscribe link silently unsubscribed
  members until 2026-10-14 (W1). Enforced by
  `python3 tools/get_write_scan.py` (MUST print nothing; the commit hook runs
  it when `api/Endpoints` or `public-web/app/api` change); a deliberate,
  harmless case carries `get-ok: <why>`.
- **Every write SP declares its pattern** on one header line,
  `-- Idempotency: <pattern> — <why>`, with `<pattern>` one of `client-id`,
  `set-state`, `compare-and-set`, `send-id`, `locked-upsert`, `log-only`,
  `read-only`, `exempt` — and its contract says the same. Enforced:
  ```bash
  python3 tools/idempotency_scan.py     # MUST print nothing
  ```
  It flags a write SP with no declaration and a check-then-INSERT whose
  `EXISTS` takes no `UPDLOCK` (silence one deliberately with
  `-- idem-ok: <why>`). The commit hook runs it when `db/hc6` changes and
  `tools/deploy_hc6.sh` refuses to deploy while it prints. Procedures written
  before the rule are grandfathered in `tools/idempotency_baseline.txt`,
  which only shrinks: touch one, declare it, fix its lock, and
  `--update-baseline`. Never add to it by hand.
- The audits behind this (app, portal, public web — what each client
  retries, and every fix) are `docs/idempotency-audit-2026-10-14.md`.

**Generated email addresses are shown in dark red and never sent to (every client):**

An account's email is its key, so a hasher with no address still gets a
made-up one: `hc-…@noemail.invalid` (import), `URC:…`, `removed_…`,
`<GUID>@harriercentral.com`, `anonymous …@harriercentral.com`. Wherever an
address is displayed, a generated one is dark red (`kGeneratedEmailColor`) and
the page carries `GeneratedEmailNote` ("Dark red email addresses have been
auto-generated and will not be used for sending emails" — James, 2026-10-10).
Senders leave them out (`HC6.IsGeneratedEmail`) and both API mailers refuse
them (`GeneratedEmail.Is`). The rule exists in FOUR copies that must change
together: `db/schema/functions/HC6.IsGeneratedEmail.Function.sql`,
`api/Endpoints/HcEmail.cs`, and `lib/util/generated_email.dart` in the portal
and the app. A new screen that shows an address uses `emailTextStyle()`.
